# Languages other than English

Scoping of 2026-11-17: how the Weishaupt definitions can exist in French first, and in any
other language by the same mechanism. Each statement is marked **run** (done in this pass),
**read** (source code or file read) or **inferred**.

**State on 2026-11-17 (evening): option A is implemented locally** (section 7). French exists
as `src/fr.yaml` on the branch `weishaupt-L`, the checks and the release script know about
translation files, the terms are recorded in `evidence/terms.md`. Nothing is pushed or
published. Sections 1 to 6 are the scoping as it was written; where the implementation found
otherwise, section 7 says so.

## 1. How translation works today

### In the library (`ebus-typespec`, emitter)

- **read** The emitter option `translations` takes one YAML file: a flat map, English text as
  key, translated text as value (`src/csv_emitter.ts`, `getEbusdEmitterClass`). When key and
  value both end with a full stop, the pair without it is added too.
- **read** Only doc comments are looked up (`#getDoc`): the comment of a message, of a field
  (property, or the scalar or model it is typed with), of an include. The lookup is on the
  whole string, exact and case-sensitive. There is no pattern, no per-file or per-circuit
  scope: a key applies to every file of the tree.
- **read, run** A string without a key is emitted in English, without warning. A key that
  matches nothing is ignored, without warning.
- **read** Not translatable: message, field and circuit names; value-list entries (emitted
  from the enum member names); units; the `[WCRC]` marker, which is put in front of the
  comment after translation (**run**: `[WCRC] temps de blocage minimal du brûleur`).
- **run** A translated comment with a comma or a quote is escaped like an English one.

### In `ebusd-configuration`

- **read** `src/de.yaml` (3006 keys, 1191 of them with the value equal to the key) is the
  only translation file compiled. `npm run compile-en` and `compile-de` give `outcsv` and
  `outcsv.de`; `utils/precheck.sh` arranges them as `en/` and `de/`. `src/en.yaml` and
  `src/i18n.yaml` are left over from the conversion of the old CSV files.
- **read** `guidelines.md`: declarations in English only, "optionally one i18n YAML file per
  supported language". A third language fits the stated design; nothing compiles or
  publishes one.
- **read** The only workflow, `check.yml`, compares `latest/de` with `latest/en` (same
  templates, line counts and names) and runs on those paths only.

### In ebusd

- **read** `--configlang=LANG` (default: environment `LANG`), normalised to two letters.
- **read** With the default configuration path (the CDN), the language picks the folder:
  `en`, otherwise `de` (`src/ebusd/main.cpp`, `lang != "en" && lang != "tt" ? "de" : lang`).
  French cannot be served from the CDN without a change in ebusd and a `fr/` folder there.
  Another HTTP path gets `?l=<lang>`.
- **read** With a local `--configpath`, ebusd loads what is in the folder; the language does
  not select a folder. A French folder works with a stock ebusd.
- **read, run** A CSV file may hold several languages: a header column `comment.fr` next to
  `comment` replaces it when the preferred language is `fr`, and is skipped otherwise
  (`MessageMap::getFieldMap`, same code for field columns and templates; any two-letter
  code). Tried with a two-language test file and `--configlang=fr`, `en` and none. The
  emitter does not produce such columns.

### What reaches Home Assistant

- **read** The MQTT definition variables include `%messagecomment` and `%comment`
  (`mqtthandler.cpp`), but the stock `mqtt-hassio.cfg` does not use them: the entity name is
  `%name %fieldnamemult`, that is message and field names, and the options of a select are
  the value-list entries. With the stock file, a French CSV changes nothing in what Home
  Assistant shows.
- **inferred** French comments are visible in `find -v`, in the JSON definitions of the HTTP
  port and in `--dumpconfig` (**run** for the last). To show them in Home Assistant, the MQTT
  configuration file must use the comment as entity name, or the integration translates on
  its side; both belong to the Home Assistant project. Value-list entries are also what a
  write expects, so they must stay as they are in the CSV.

### Summary

| Need | Supported as it is | Needs a change in |
|---|---|---|
| French comments in a CSV set loaded from a local path | yes | this project's release only |
| German comments for the lots in the upstream German build | yes | `src/de.yaml` entries in each lot |
| French from the default path of ebusd | no | ebusd (CDN folder choice), upstream publication |
| One CSV set with several languages | ebusd yes | the emitter (extra columns) |
| Translated value lists, units, names | no | not wanted: names and values are the interface |
| French entity names in Home Assistant | no | MQTT configuration file or the integration |

## 3. Terminology

A French installer expects the vendor's words. Sources, best first:

1. **Vendor manuals in the target language.** `evidence/settings-writes.md` already cites the
   German editions for the settings: system manager manual, document 83258401, and room unit
   manual, document 83277701. **Inferred**: the vendor numbers a manual with a language
   suffix (German editions end in 01; French documents seen in the vendor's online library
   end in 04 or 05). **Not found** in one web search: the French editions of these two. To
   obtain from the vendor's document library or the paper manuals of an installation.
2. **Display texts of the controllers.** The room units and the system manager show setting
   names on their display; where the display language can be set, the French text is the
   reference for that setting. Reading a display is the operator's task.
3. **Vendor service tool.** `evidence/service-tool-log.md` records the labels of the tool's
   screens, in English on the PC used ("De-couple temperature B22", "DHW set value"). No
   language file was found in its folder; whether the tool has other languages is not known.
4. Otherwise a **provisional** translation with ordinary heating vocabulary, marked as such.

Recording, in the spirit of rule 3 and without copying vendor documents: one glossary record,
`evidence/terms.md`, one row per term (not per string): English term used in the lots, German,
French, source (manual title, document number, page; or device and software version whose
display shows it; or the service-tool session), status `vendor` or `provisional`. A
translation file is built from the glossary: a string enters `fr.yaml` only when its terms
have a row. About 60 terms cover the 130 hand-translated strings. Citing a term with its
document and page is a citation, not a copy.

## 4. Options

| | A. `fr.yaml`, French archive in the fork's release | B. German entries for the lots | C. More languages upstream | D. Multi-language CSV | E. Home Assistant only |
|---|---|---|---|---|---|
| What the owner gets | French comments in ebusd from a local path, any language by adding a file | complete German build, for the fork and upstream | French for every ebusd user from the default path | one archive, language chosen by `--configlang` | French names in Home Assistant, nothing in ebusd |
| Changes | `release.sh`: one compile, check and archive per language; `check.sh`: key check | 255 keys in `de.yaml`, in the lot that adds the string | `fr.yaml` and `compile-fr` upstream, CDN `fr/`, one line in ebusd | emitter option and columns; release unchanged in layout | none here |
| Upstream | the file can be proposed later (C) | yes, with each lot; question open in #717 | needs the maintainer on three repositories | library pull request | no |
| Cost when a lot changes | changed string: its key and each language; caught by the key check | same, inside the lot | same as A | same as A | follows names, not comments |

Recommendation: **A now, B when the maintainer answers, C as a question only, D not now.**

- A needs no change in the library or in ebusd and reaches every user of the fork's release.
- B is the part upstream can take today. German is the vendor's first language, so the
  glossary gives it almost for free; write the German column of the glossary with the French.
- C depends on a maintainer who has not reviewed lot A yet. Ask once #717 has an answer.
- D is the cleanest result and ebusd supports it, but it is a library feature to design and
  maintain in the fork for a gain (one archive instead of two) that does not matter yet.

Not to do: translate value-list entries or names (they are what `read`, `write` and MQTT
use); write French in the TypeSpec comments; edit compiled CSV; put `fr.yaml` keys into the
lot branches that back upstream pull requests; publish vendor texts.

One side effect to accept: keys are global, so `temperature: température` also translates
that comment in the files of other manufacturers. The release archive ships only the root
files and the Kromschröder folder, so it shows in `broadcast.csv` at most.

## 6. Implementation plan

Decisions the owner takes first:

1. Languages of the first step: French only, or French and German together (recommended:
   both in the glossary, French in the release, German kept for the lots).
2. Release layout: one more archive per language, `weishaupt-ebusd-config-<version>-fr`,
   the English one unchanged (recommended), or one archive with `en/` and `fr/` folders as
   on the CDN, which changes the layout users of 0.2.0 know.
3. Terminology: who obtains the French manuals or reads the displays, and whether a first
   French release may carry provisional terms marked in the notice.
4. Where `fr.yaml` lives: a branch of its own on top of the stack, `weishaupt-L`
   (recommended; no upstream pull request for it), or inside each lot.
5. Whether to ask upstream about a third language, and when (rule 8).
6. For the Home Assistant project: comment as entity name, or translation on its side.

Steps, each checkable on its own:

1. `evidence/terms.md`: glossary of the terms of the 130 strings, German and French, source
   and status for each.
2. Workbench script that lists, from a compiled English tree, the comment strings of the lot
   files, and compares them with a translation file: missing keys, keys that match nothing.
   The second kind fails `scripts/check.sh`; the first is reported as coverage.
3. `src/fr.yaml` on the branch of decision 4: the patterned entries written by the script,
   the others from the glossary. Replace the prototype file.
4. `scripts/check.sh`: for each `src/<lang>.yaml` that has keys of the lot folder, compile
   with it, run `--checkconfig`, and compare with the English CSV: same lines, same message
   count, every column other than the comments identical.
5. `scripts/integrate.sh`: the new branch in `STACK`, or applied after the stack if it must
   stay out of it. `scripts/release.sh`: one archive per language, the notice
   (`docs/release-readme.md`) says how to choose and which terms are provisional.
6. Release on the owner's word; download again and load each archive in the official ebusd.
7. When the maintainer answers on `de.yaml`: German keys added to each lot, from the glossary.

Size: 261 keys per language, about 130 by hand from some 60 terms; steps 2 to 5 are one
working session; step 1 depends on getting the French sources. Maintenance: a changed
comment in a lot breaks its key, which step 2 reports.

### What the implementation found

- **252 strings, not 261.** Section 2 counted a comment with and without the `[WCRC]` marker as
  two strings. The emitter looks the comment up without the marker: 228 strings belong to the
  lots, 24 are the Wolf messages of upstream that share `wolf/broadcast`.
- **Coverage**: 160 strings use vendor terms only, 68 strings of the lots are provisional (20
  written by hand, 48 patterned: "stored in the room unit" and the fault-history slots), and
  the 24 Wolf strings are translated without a vendor source. None is missing.
- **Stack or after it**: in the stack. `weishaupt-L` adds one file that no lot touches, so the
  stack stays linear and `integrate.sh` needs no second mechanism; the integration branch then
  holds what the release compiles, in one commit id. The condition of section 4 is met another
  way: no upstream pull request is cut from `weishaupt-L`, and a new lot is inserted below it
  (rebase `weishaupt-L` onto the new top, regenerate the patterned entries, the key check says
  what changed).
- **Side effect of global keys** (announced in section 4): in the French tree, `temperature`
  and a few other one-word comments are also translated in the general `broadcast.csv` and in
  the files of other manufacturers. The archive ships the root files and the Kromschröder
  folder only.
- **German**: `de.yaml` has 6 keys of the lot strings by coincidence, so the check also
  compiles a German tree and loads it. No German archive is built.
- **Manuals**: the French editions the operator has cover the system manager, the room unit
  with the heating module, the boiler and the hydraulic separation. English editions exist for
  the room unit and the boiler only. Missing: the French user manual of the room unit (its
  time-program screens), any German edition.
